\chapter{Especificación de Requisitos del Software}\label{requisitos}

\azul{Este capítulo documenta las propiedades, servicios y restricciones operativas que el artefacto informático debe exhibir. La ingeniería de software postula que una especificación rigurosa constituye el contrato técnico fundamental para el desarrollo, mitigando desviaciones estructurales en fases avanzadas del ciclo de vida \cite[p.~83]{sommerville2011ingenieria}. Se sugiere acompañar la redacción con modelos UML, puesto que la representación gráfica podría indicar con mayor precisión la arquitectura del sistema.}

\section{Interfaces Externas (\rojo{Opcional})}

\azul{Esta sección detalla los protocolos, formatos y mecanismos mediante los cuales el sistema interactúa con su entorno operativo, abarcando operadores humanos, dispositivos físicos, aplicaciones complementarias y redes de comunicación \cite[p.~10]{ieee830_1998},\cite[p.~150]{pressman2010ingenieria}.}

\subsection{Interfaces de Usuario}

\azul{Describe las características lógicas y físicas de la interfaz con la que interactuará el usuario final. Se deben especificar aspectos como el tipo de interfaz (web, móvil, de consola), los principios ergonómicos o de accesibilidad aplicados, el flujo de navegación, los requerimientos de diseño visual y las reglas de presentación de información o captura de datos.}

\moradoc{Ejemplo: La interfaz de usuario consistirá en un panel web responsivo optimizado para resoluciones de pantalla estándar y dispositivos móviles. El diseño adoptará componentes gráficos basados en el sistema de diseño Material UI, garantizando tiempos de carga reducidos y compatibilidad con lectores de pantalla según la pauta WCAG 2.1.}

\subsection{Interfaces de Hardware}

\azul{Especifica las características lógicas y físicas del soporte de hardware que requiere el software para su operación o integración. Incluye tipos de dispositivos soportados, sensores, actuadores, frecuencias de muestreo, direcciones de memoria, rangos de voltaje o protocolos de comunicación a nivel de circuito.}

\moradoc{Ejemplo: El sistema se conectará a un módulo sensor de flujo mediante una interfaz serie UART/RS-485 operando a una velocidad de transmisión de 9600 baudios, 8 bits de datos, sin paridad y 1 bit de parada (9600-8-N-1).}

\subsection{Interfaces de Software}

\azul{Detalla las conexiones con otros productos de software o sistemas legados, tales como bases de datos, servicios web externos, bibliotecas del sistema operativo o marcos de trabajo específicos. Se debe indicar el nombre, versión y propósito de cada componente externo, además de las estructuras de datos o servicios compartidos.}

\moradoc{Ejemplo: La aplicación conectará con la API RESTful del sistema de autenticación institucional mediante solicitudes HTTP/HTTPS codificadas en formato JSON, empleando tokens JWT (JSON Web Tokens) para el control de sesiones.}

\subsection{Interfaces de Comunicación}

\azul{Define los requerimientos para los enlaces y protocolos de red utilizados por la solución. Especifica los niveles de red (modelo OSI o TCP/IP), puertos de escucha, tasas de transferencia esperadas, formatos de paquetes de red y mecanismos de cifrado o tunelización para la transmisión de datos.}

\moradoc{Ejemplo: Las transmisiones de datos telemétricos entre los nodos distribuidos y el servidor central utilizarán el protocolo ligero MQTT sobre socket seguro TLS (puerto 8883), implementando una calidad de servicio QoS de nivel 1 para mitigar la pérdida de paquetes.}

\section{Requisitos Funcionales (\rojo{Obligatorio})}

\azul{Los requisitos funcionales describen los servicios específicos que el sistema proveerá frente a entradas particulares. Su redacción exige un lenguaje técnico inequívoco, estructurado mediante identificadores alfanuméricos únicos para asegurar la trazabilidad de los componentes durante la fase de pruebas de validación.}

\moradoc{Ejemplo de Requisitos Funcionales:
	\begin{itemize}
		\item \textbf{RF-01:} El módulo de autenticación debe validar las credenciales del usuario contrastándolas mediante un algoritmo de hash criptográfico.
		\item \textbf{RF-02:} El sistema debe exportar los registros de transacciones diarias en un documento estructurado bajo formato PDF.
\end{itemize}}

\section{Requisitos de Rendimiento (\rojo{Opcional})}

\azul{Estas especificaciones delimitan las métricas de eficiencia computacional del sistema, abordando dimensiones como tiempos de respuesta, consumo de memoria o tolerancia a la concurrencia de sesiones. Una definición ambigua en este apartado podría desencadenar fallas críticas durante el despliegue.}

\moradoc{Ejemplo: La arquitectura de microservicios debe procesar al menos 500 peticiones concurrentes de consulta, manteniendo un tiempo máximo de respuesta inferior a 2,5 segundos por transacción.}

\section{Requisitos de Desarrollo (\rojo{Opcional})}

\azul{El apartado impone directrices metodológicas o normativas sobre el ciclo de construcción. Esto integra aspectos como estándares de codificación institucional, flujos de integración continua o el empleo de repositorios de control de versiones centralizados.}

\section{Requisitos Tecnológicos (\rojo{Obligatorio})}\label{requtec}

\azul{La investigación declara explícitamente el conjunto de lenguajes de programación, marcos de trabajo y herramientas que cimentarán la solución. Esta selección tecnológica debe guardar estricta coherencia con la viabilidad técnica analizada en las fases previas del proyecto.}

\moradoc{Ejemplo de Pila Tecnológica:
	\begin{itemize}
		\item \textbf{RT-01:} La lógica de negocio (Backend) se programará en Python, utilizando el marco de trabajo Django.
		\item \textbf{RT-02:} La capa de presentación (Frontend) implementará componentes reactivos mediante React.
		\item \textbf{RT-03:} La persistencia de datos relacionales operará bajo el motor PostgreSQL.
\end{itemize}}

\section{Seguridad Informática (\rojo{Obligatorio})}

\azul{Se requiere estructurar los mecanismos de protección del sistema contra accesos no autorizados, inyección de código o pérdida de integridad de los registros. Esta dimensión adquiere particular relevancia frente al manejo de datos sensibles institucionales.}

\moradoc{Ejemplo de Seguridad:
	\begin{itemize}
		\item \textbf{RS-01:} Las contraseñas se almacenarán aplicando la función de derivación de claves Bcrypt con un factor de costo igual a 12.
		\item \textbf{RS-02:} Las comunicaciones entre la aplicación cliente y la API se cifrarán obligatoriamente mediante el protocolo TLS 1.3.
\end{itemize}}
